### 2. The Hierarchy & Roles
* **Tier 1: Super User (SaaS Owner / Global Admin)**
    * Has a global dashboard.
    * Can create, suspend, and manage "Company Accounts" (Tenants).
    * Monitors overall system health, billing, and global configurations.
    * Cannot access a company's internal operational data unless explicitly granted for support.
* **Tier 2: Company Admin (Tenant Root)**
    * Represents the organization that bought the software.
    * Can create, update, and delete "Managers" within their own company.
    * Configures company-specific security settings (e.g., password policies, session timeouts, allowed IP ranges, or MFA requirements).
    * Strictly isolated: Must never be able to see or interact with any other company's data.
* **Tier 3: Manager**
    * Created by the Company Admin.
    * Responsible for registering, managing, and monitoring "End Devices."
    * Has read/write permissions for devices, but cannot modify company-level settings or manage other managers.
* **Tier 4: End Devices**
    * Hardware or software endpoints registered by a Manager.
    * Must be uniquely tied to a specific Company ID and assigned to a Manager/Location context.
    * Authenticates via a secure token/key mechanism (e.g., API keys or MTLS) to report data or receive commands.

### 3. Core Architectural Requirements
* **Multi-Tenancy Security:** Detail how data isolation will be enforced at the database level. (Explain whether to use a logical separation via a `tenant_id` foreign key on every table, or separate schemas).

* **Device Onboarding Flow:** Outline a secure workflow for how a Manager generates a registration token, how the End Device uses that token to register itself, and how it receives its unique device credentials.
